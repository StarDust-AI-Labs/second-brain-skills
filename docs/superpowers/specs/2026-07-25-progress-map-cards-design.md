# 工作流步骤链可视化（Progress Map Cards）设计

- 日期：2026-07-25
- 状态：Codex 审核有条件通过，待按第 8 节修订后写实现计划
- 范围：`second-brain-hub` Skill 的全部 8 个知识管理场景

## 1. 背景与目标

`second-brain-hub` 是第二大脑体系的唯一入口，支持 8 个场景：灵感速记、保存外源、提炼加工、创作启动、收件箱处理、回顾整理、探索查询、系统诊断。

现状：执行过程已有"处理痕迹"（`output-cards.md` 的开始/进度/决策/完成卡 + `Hub Run Ledger` 台账），但存在三个问题：

- 进度卡片是**可选**的，各场景输出节奏不统一
- 格式简陋（纯文本【进度】x/y），无全局视图，用户看不到"总共几步、走到哪"
- 排版无规范，缺乏美化

**目标**：把"工作流执行过程可视化"升级为一套规范化、有统一排版的进度展示系统。让用户在聊天框中清晰看到 AI 正在调用 skill 处理知识的**每一步**，且每一关键步骤都留下可见的处理痕迹。

## 2. 第一准则：自主决策自由 + 痕迹强制

系统可**自主**决定阻塞、降级、跳过、重试，但**每一个决策都必须在地图上留下可见痕迹**。用户看到的不是"无错误执行"，而是"发生了什么、为什么"。**禁止任何形式的静默处理。**

该准则优先级高于排版美观，是整套规范的核心。三类强制留痕：

| 决策 | 地图表现 |
|---|---|
| 阻塞 | `❌` + 阻塞原因 + 给用户的出路（重试/降级/终止），不静默跳步 |
| 降级 | `✅` + 痕迹注明"(降级：用 XX 替代，原因)"，透明告知 |
| 跳过 | `⤳ 已跳过` + 契约跳过证据（对应 `optional_steps_skipped`） |

## 3. 核心卡片格式（用户可见）

### 3.1 步骤链地图卡

每个场景在**关键步骤边界**输出统一的"步骤链地图卡"：

```text
【灵感速记】步骤 3/5

  ✅ 1 确认归属     → Projects/产品迭代
  ✅ 2 价值判断     → 符合长期兴趣
  ▶ 3 渲染模板     ← 进行中
  ⬜ 4 写入笔记
  ⬜ 5 保存回执

  痕迹：已生成标题「灵感-订阅制复盘_2026-07-25-2113」
```

### 3.2 状态图标（每步一个，克制使用）

- `✅` 已完成 → 后面跟该步留下的关键痕迹/产出
- `▶` 进行中 → 后面跟 `← 进行中`
- `⬜` 未开始
- `❌` 阻塞 / `⤳` 跳过

### 3.3 emoji 克制规则

**状态图标保留**（✅▶⬜❌⤳ 是进度的核心视觉语言），**去掉装饰性 emoji**（🧠💾 等纯点缀），文字标签承担信息。单卡 emoji 控制在 3–5 个状态符号，每步仅一个。

### 3.4 四类卡片

- **开始卡**：场景启动时先亮出完整地图（全部 ⬜），让用户预知总步骤数
- **进度卡**：每完成一个关键步骤刷新一次地图
- **完成卡**：全部 ✅，痕迹替换为最终交付物 + 位置 + 下一步
- **决策卡**：需用户选择时，地图暂停在当前步，下方挂【需要你决定 / 我的建议 / 可选项】

### 3.5 节奏与 token 预算

- 进度卡只在**步骤边界**刷新，步骤内部不刷
- 单场景全程地图卡 ≤ 步骤数 + 2（开始 + 完成）
- 步骤数控制在 **4–7 步**，过多则合并，避免刷屏

## 4. 8 个场景的步骤链定义

每个场景把契约步骤映射为一条 4–7 步的固定链：

| 场景 | 步骤链 |
|---|---|
| 灵感速记 | 确认归属 → 价值判断 → 渲染模板 → 写入笔记 → 保存回执 |
| 保存外源 | 抓取内容 → 价值判断 → 提炼要点 → 渲染模板 → 写入归档 → 保存回执 |
| 提炼加工 | 读取笔记 → 分层提炼 → 标亮重点 → 回写笔记 → 保存回执 |
| 创作启动 | 明确主题 → 检索素材 → 搭建大纲 → 生成初稿 → 写入归档 |
| 收件箱处理 | 扫描收件箱 → 逐条分类 → 批量归档 → 清理汇总 |
| 回顾整理 | 收集周期笔记 → 归纳主题 → 提炼洞察 → 生成回顾 → 写入归档 |
| 探索查询 | 解析意图 → 检索知识库 → 关联匹配 → 汇总结果 |
| 系统诊断 | 采集现状 → 定位瓶颈 → 匹配 CODE 环节 → 给出建议 |

### 关键设计决策

- **单一事实源**：执行步骤与显示映射都由 `route-contracts.json` 提供；工作流只解释痕迹语义，`output-visualization.md` 只定义格式规则
- **测试与生产隔离**：生产 Skill 不包含评测模式、测试协议或期望答案；runner 从 `tests/hub/harness/` 外部注入评测要求

## 6. 错误处理与边界情况

| 场景 | 可视化行为 |
|---|---|
| 步骤失败/门控阻塞 | 当前步 `❌`，痕迹写阻塞原因，地图停住，决策卡引导用户，不静默跳步 |
| 安全降级 | 该步 `✅` 但痕迹注明"(降级：用 XX 替代)" |
| 条件步骤被跳过 | 标记 `⤳ 已跳过` + 跳过证据，不显示为未完成 |
| onboarding 首次引导 | 不套场景地图（还没进入场景），沿用 onboarding 自己的引导卡，避免两套可视化打架 |
| 系统诊断（只读） | 地图正常显示，但完成卡的"位置"省略 |
| 步骤回退/追问 | 不刷新地图刷屏，只在原地图基础上更新当前步状态 |

## 7. 验证方式

- 通过仓库外部行为 harness 校验：8 个场景每个都断言"按时序输出地图卡、步骤名与契约一致、状态流转正确、阻塞/降级/跳过均留痕"
- 纳入现有测评回归，防止规范腐化
- 人工抽查真实对话，确认排版美观且不刷屏

## 8. Codex 审核备注（2026-07-26）

### 8.1 审核结论

**有条件通过。** 核心方向成立：将工作流过程从零散进度提示升级为可预期、可追踪、可审计的步骤地图，尤其是“阻塞、降级、跳过必须留痕”的原则，值得纳入本次大版本。

开发前必须先落实下面四项 P0，避免可视化层与现有契约漂移，或引入无法量化测试的新行为。

### 8.2 P0 修改要求

#### P0-1：以 `route-contracts.json` 为机器事实源

当前第 5 节提出在 8 个 `workflow-*.md` 中分别维护显示步骤，但实际运行时的机器步骤已经由 `route-contracts.json` 的 `step_order`、`required_steps` 和 `conditional_steps` 定义。如果再手写一份显示链，会形成两个事实源。

建议在场景契约中增加显示映射，例如：

```json
{
  "progress_map": [
    {
      "display_id": "render-note",
      "label": "渲染模板",
      "source_steps": ["obsidian-markdown"]
    }
  ]
}
```

`workflow-*.md` 只解释每个显示步骤应留下什么痕迹，不再重复定义顺序。验证器必须断言每个 `source_steps` 都来自该场景的 `step_order`，且所有必选步骤均被覆盖。

#### P0-2：定义可机器验证的进度事件

现有行为 Trace 只有最终契约结果，无法验证“何时输出了哪张卡、状态如何流转”。应在 `tests/hub/` 的外部评测 Schema 中新增结构化事件；生产 Skill 只定义用户可见行为，不包含测试字段和断言。例如：

```json
{
  "progress_events": [
    {
      "sequence": 1,
      "display_id": "target-routing",
      "label": "确认归属",
      "state": "completed",
      "trace": "归属第二大脑体系搭建",
      "reason": null
    }
  ]
}
```

`state` 至少支持 `pending`、`in_progress`、`completed`、`skipped`、`blocked`。降级可以使用 `completed`，但必须额外记录 `fallback` 与原因。测试应校验事件顺序、合法状态迁移、痕迹非空，以及阻塞后不得继续执行后续步骤。

#### P0-3：显示步骤不得改变业务语义

第 4 节的显示链需要逐场景与契约重新对齐：

- 灵感速记的“价值判断”是条件步骤，未触发时应显示跳过证据，不能伪装为必做步骤。
- 创作启动不一定生成“初稿”；契约允许输出大纲或下一产物，显示名称应使用“形成创作产物”等不扩大范围的表达。
- 收件箱处理不一定“批量归档”，还可能逐条移动或等待删除确认，显示步骤不能绕过安全门禁。
- 探索查询的长期问题匹配是条件能力，未配置长期问题时应显示跳过，而不是固定显示为已执行。

建议给每个显示步骤同时声明 `required`、`conditional` 或 `summary` 类型，并由契约条件决定最终状态。

#### P0-4：可视化规范必须按需加载并受预算约束

当前固定上下文已经达到 `14127 / 13000 bytes`，现有静态门禁失败。新增 `output-visualization.md` 不得进入固定加载集合，应只在场景确认后按需读取。本次优化将固定预算进一步收紧为 `10000 bytes`，为后续版本保留余量。

除“地图卡数量 ≤ 步骤数 + 2”外，还应增加可量化预算：

- 单张地图卡最大字符数；
- 单场景所有地图卡累计字符数或 token 数；
- 相邻卡片只允许必要的状态变化，不重复长痕迹；
- 固定上下文恢复到 `≤ 10000 bytes` 后才允许合入。

### 8.3 本特性验收标准

1. 8 个场景均存在由契约派生的 `progress_map`，必选步骤覆盖率 100%。
2. 条件步骤的执行与跳过、工具降级、门控阻塞均有结构化事件和用户可见痕迹。
3. 非法状态迁移、阻塞后继续执行、显示步骤引用未知契约步骤时，测试必须失败。
4. 8 个黄金场景和阻塞、降级、跳过用例均通过可视化回归。
5. `validate-test-prompts.ps1`、初始化成功校验和行为评测门禁全部通过。
6. 固定上下文不超过 `10000 bytes`，且地图卡不造成明显刷屏。
